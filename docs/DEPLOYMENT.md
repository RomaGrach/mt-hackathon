## Адрес демонстрации

Основной адрес, предоставленный владельцем 27.09.2026: **https://5.42.113.212:9443/**.

При проверке HTTPS-запрос `/api/health` вернул HTTP 200 и `status: ok`, `engine: shift-4`, `storage: sqlite`. Браузер открыл главную, создал учебный профиль и начал смену. Проверка выполнялась с обычной валидацией TLS, без отключения проверки сертификата.

Точная конфигурация reverse proxy, менеджер процесса, каталог установки и commit работающего сервера не предоставлены. Health подтверждает движок, но не SHA сборки. Следующие команды — воспроизводимая инструкция для владельца сервера, а не утверждение о выполненном нами переносе.

## Локальный запуск

Нужен Node.js 24. Из корня репозитория:

```sh
node server.mjs
```

По умолчанию приложение слушает `127.0.0.1:3000`, данные сохраняются в `data/reis400.sqlite`. npm-зависимости нужны для сборки и разработки, а не для этого запуска.

## HTTPS на сервере

1. Получите нужный commit репозитория и установите Node.js 24.
2. Выберите постоянный каталог БД вне сменяемого каталога релиза.
3. Настройте переменные окружения. Для текущего адреса:

```dotenv
HOST=127.0.0.1
PORT=3000
DB_PATH=/var/lib/reis400/reis400.sqlite
PUBLIC_ORIGIN=https://5.42.113.212:9443
COOKIE_SECURE=true
NODE_ENV=production
```

Путь `/var/lib/reis400` — пример: создайте каталог с правами сервисного пользователя. Не переносите его буквально в существующую установку без сверки с действующим `DB_PATH`.

4. Запускайте `node --env-file=.env server.mjs` через выбранный менеджер процессов.
5. Настройте HTTPS reverse proxy для статики и `/api` на один upstream `127.0.0.1:3000`. Сертификат должен быть действителен для внешнего адреса.
6. Проверьте главную, `/api/health`, создание профиля и прохождение смены.

В коде есть локальный rate limit: не более 100 новых профилей в час с одного IP и 1000 в час для всего процесса. Если соединение приходит с loopback, приложение принимает только корректный `X-Real-IP`, который nginx должен перезаписывать значением `$remote_addr`. Не проксируйте публичный клиентский `X-Real-IP` без перезаписи и не открывайте backend-порт наружу.

## Обновление существующей установки

1. Запишите текущий SHA, конфигурацию запуска и путь БД.
2. Сделайте корректную SQLite-резервную копию. При файловом копировании предварительно остановите процесс; учитывайте WAL. Не копируйте только основной файл работающей БД.
3. Получите новый commit, не затирая локальные изменения и `.env`.
4. Выполните `npm run check` и `npm test` на выбранном коде. При необходимости сборки frontend: `npm ci`, затем `npm run build:site`.
5. Перезапустите приложение прежним менеджером процессов с прежним `DB_PATH`.
6. Проверьте health, новую смену, диалог, итог и восстановление существующего профиля после reload.
7. Сохраните SHA и результат проверки в журнале выпуска. Изменение GitHub само по себе не обновляет этот сервер.

При откате сначала проверьте совместимость схемы/контента. Возврат к старому коду не означает, что он умеет читать новую БД; восстановление backup потеряет данные, записанные после него.

## Docker

```sh
docker compose up --build -d
```

Compose публикует порт только на `127.0.0.1:3000`; внешний HTTPS настраивается отдельно. Данные — в томе `game-data`. `docker compose down -v` удаляет этот том. Контейнерный запуск последнего релиза в проверочной среде не выполнялся.

## Альтернативное размещение Sites

Существующий Site сохранён как дополнительный канал: https://mt-hackathon.realeurguy.chatgpt.site.

Он имеет **отдельную базу и отдельный процесс публикации**. Профили между двумя адресами не синхронизируются. Его Worker использует SQL.js и сжатый snapshot в D1; это не SQLite-файл основного сервера. Ограничения snapshot и порядок публикации описаны в [SITES-DEPLOYMENT.md](SITES-DEPLOYMENT.md). Для сдачи используйте основной адрес выше.
