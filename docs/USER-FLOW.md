# User Flow — РЕЙС 400 / Design002

Этот документ описывает актуальный пользовательский путь конкурсной версии: **design002@1.3.0**, движок **shift-4**. Старое описание последовательного v1-прототипа больше не является основным сценарием.

Ключевой принцип продукта: игрок не проходит тест из независимых вопросов. Он управляет ограниченной сменой, где одновременно конкурируют за внимание пассажирские ситуации, скрытые проблемы и рабочие обязанности.

## 1. Полный путь пользователя

~~~mermaid
flowchart TD
  A[Первый вход] --> B[Синтетический профиль]
  B --> C[Главная]
  C --> D[Курс: следующая смена]
  C --> E[Своя тренировка]
  C --> P[Профиль / прогресс / рейтинг]
  D --> F[Выбор условий сервером/курсом]
  E --> G[Класс + вариант + критический таймер]
  F --> H[Автоматический старт]
  G --> H
  H --> I[Смена: Дела]
  I --> J{Выбрать рабочее действие}
  J --> K[Известная проблема]
  J --> L[Рабочая задача]
  J --> M[Осмотр вагона]
  K --> N[Решение / диалог / последствия]
  L --> O[Выполнение обязательства]
  M --> Q[Обнаружение скрытых проблем]
  Q -->|Решить одну найденную| N
  Q -->|Закончить осмотр| R[Следующий такт]
  N --> R
  O --> R
  R --> S[Автоисходы просроченных дел]
  S --> T{Остались такты?}
  T -->|Да| I
  T -->|Нет| U[Итоговый разбор]
  U --> V[Очки компетенций]
  V --> P
~~~

## 2. Вход и профиль

На первом входе приложение создаёт синтетический учебный профиль. Реальные ФИО или кадровые данные для демонстрации не нужны.

Профиль хранит:

- накопленные очки компетенций;
- уровень;
- историю смен;
- результаты и итоговые шкалы;
- типовые ошибки;
- невыполненные задачи;
- место в рейтинге своей группы.

Если у пользователя уже есть незавершённая серверная смена, интерфейс предлагает продолжить её, а не создаёт вторую попытку.

## 3. Главная

На главной пользователь видит две основные точки входа:

1. **Курс** — последовательность готовых тренировок возрастающей сложности.
2. **Своя тренировка** — выбор параметров смены.

Текущие варианты Design002:

| Вариант | Такты | Назначение |
|---|---:|---|
| orientation | 8 | Первое знакомство |
| service | 10 | Обслуживание и обязательства |
| attention | 16 | Несколько дел одновременно |
| full | 20 | Полная смена |

Доступны четыре класса обслуживания: standard, comfort, business, first.

Для критических ситуаций выбирается реальный серверный таймер:

- standard — 60 секунд;
- extended — 120 секунд.

## 4. Начало смены

После создания run сервер уже сформировал конечный набор проблем смены, но скрытые ситуации и будущие переходы пользователю не раскрываются.

Одно нажатие **«Начать смену»** создаёт попытку и автоматически начинает её. Второго подтверждения нет; правила доступны в обучении.

В начале появляются штатные задачи:

- принять вагон;
- подготовить раздачу напитков.

Приёмка имеет смысл именно как начальная обязанность: если игрок сначала тратит такт на другое рабочее действие, она закрывается как пропущенная и позже может породить связанную проблему с непроверенным креплением.

## 5. Основной экран смены

Навигация содержит четыре основных раздела:

- **Дела** — все известные открытые проблемы сверху и текущие задачи ниже;
- **Вагон** — схема мест и маркеры известных обращений;
- **Лог** — причинная история действий и последствий;
- **Меню** — состояние смены и выход.

Интерфейс намеренно **не сортирует проблемы по реальной критичности** и не показывает внутренние сроки в тактах. Игрок должен сам определить приоритет по содержанию.

На карточках нет подсказки вида «правильный выбор» или «эта проблема важнее».

## 6. Что считается тактом

Один отдельный рабочий результат стоит один такт:

- завершённый этап проблемы;
- выполнение задачи;
- завершённый осмотр.

Открытие карточки проблемы, возврат к списку и чтение лога такт не расходуют.

Отдельной команды «пропустить ход» у shift-4 нет. Каждый такт используется на рабочее действие.

После продвижения мира на один такт сервер может:

- открыть запланированную проблему;
- закрыть просроченную проблему худшим исходом;
- закрыть просроченную задачу;
- создать связанную проблему;
- применить последствия к loyalty / safety.

## 7. Осмотр вагона

Часть ситуаций скрыта и не появляется в списке, пока игрок не выполнил осмотр.

~~~mermaid
flowchart TD
  A[Осмотреть вагон] --> B{Найдены скрытые проблемы?}
  B -->|Нет| C[Осмотр завершает 1 такт]
  B -->|Да| D[Все найденные становятся известными]
  D --> E{Что сделать в рамках осмотра?}
  E -->|Решить одну найденную| F[Решение + осмотр = 1 такт]
  E -->|Не решать сейчас| G[Закончить осмотр = 1 такт]
  F --> H[Остальные найденные остаются в Делах]
  G --> H
~~~

Если найдено несколько проблем, можно немедленно решить только одну. Остальные сохраняются в общем списке и конкурируют за следующие такты.

Во время незавершённого осмотра остальные известные дела остаются видимыми, но недоступные действия получают объяснение.

## 8. Проблемы

Каждая проблема имеет:

- описание;
- пассажира / место / зону;
- скрытую внутреннюю серьёзность;
- скрытый срок до автоисхода;
- варианты действий;
- исход 0 / 1 / 2 балла;
- изменения loyalty / safety;
- при необходимости новые задачи;
- при необходимости следующую связанную проблему;
- при необходимости критический реальный таймер.

Диалог продолжается внутри карточки. После конечного решения здесь же остаётся **результат конкретного действия** и связанные новые задачи. Бесплатное «Окей» возвращает к делам; итог последнего действия ведёт к итогам смены. Полная цепочка сохраняется в логе.

## 9. Задачи

Задача — рабочее обязательство, а не отдельная тестовая проблема.

Примеры:

- принести плед;
- проверить, что коллега помог пассажиру;
- убрать воду;
- проверить сухость пола;
- передать сведения о дефекте;
- пополнить санитарные принадлежности.

Каждая задача:

- занимает один рабочий такт;
- имеет скрытый конечный срок жизни;
- при просрочке получает собственный отрицательный исход;
- может изменить loyalty / safety или породить новую проблему;
- **не даёт очки компетенций напрямую**.

Таким образом, хороший вариант ответа может создать будущую нагрузку. Игроку приходится учитывать не только качество текущего ответа, но и способность выполнить принятое обязательство.

## 10. Критическая ситуация

Критическая проблема начинает реальный таймер только после того, как игрок открыл её.

~~~mermaid
sequenceDiagram
  participant U as Игрок
  participant S as Сервер
  U->>S: focus(critical incident)
  S-->>U: Сцена + варианты + deadline
  Note over U,S: 60 или 120 секунд
  alt Ответ до deadline
    U->>S: choose(...)
    S-->>U: Исход выбранного действия
  else Deadline наступил
    U->>S: choose(...) или GET после возврата
    S-->>U: DEADLINE_EXPIRED + состояние после timeout
  end
~~~

Таймаут применяет худший исход именно этой проблемы. Немедленный провал всей смены происходит только там, где конкретный исход помечен фатальным.

## 11. Конец смены

После последнего доступного такта смена заканчивается сразу.

Сервер:

1. закрывает оставшиеся активные/запланированные проблемы их худшими исходами;
2. закрывает невыполненные задачи их отрицательными исходами;
3. считает итоговые loyalty и safety;
4. рассчитывает баллы каждой проблемы;
5. строит итоговый разбор.

Формула результата:

**FACT = сумма баллов проблем**

**MAX = 2 × число учитываемых проблем**

**SHIFT_SCORE = FACT / MAX × 100**

Задачи в MAX не входят.

В расчёт входят в том числе скрытые и не обнаруженные проблемы, если они реально входили в смену и не были предотвращены до возникновения.

## 12. Итоговый разбор

Разбор показывает:

- какие проблемы появились;
- какие были скрыты и обнаружены;
- что игрок выбирал;
- какие ситуации закрылись автоматически;
- какие задачи появились;
- какие задачи выполнены и провалены;
- связанные последствия;
- изменения loyalty / safety;
- критические ошибки;
- баллы 0 / 1 / 2 по каждой проблеме;
- FACT / MAX;
- SHIFT_SCORE;
- добавленные очки компетенций;
- лучшую альтернативу для неидеальных решений;
- статистику resolved / automatic / undiscovered / tasksDone / tasksMissed.

Это не просто экран «правильно / неправильно»: пользователь видит причинную связь между распределением внимания и итогом смены.

## 13. Прогресс после смены

Непрерванная полная смена добавляет нормированный результат к общему показателю:

**COMPETENCY_POINTS = сумма SHIFT_SCORE**

Пример:

- смена 1: 75;
- смена 2: 90;
- смена 3: 62;
- накоплено: 227.

Уровень профиля повышается каждые 250 накопленных очков.

Рейтинг сравнивает накопленные очки внутри crew / depot / company. Старые XP/СП раннего прототипа показываются отдельно и не смешиваются с новой системой.

# Примеры игровых сценариев

Ниже приведены реальные примеры из текущей библиотеки **backend/design002-content.js**. Они синтетические и предназначены для учебной демонстрации, а не являются официальной производственной инструкцией перевозчика.

## Сценарий A — пассажир ищет место

**Ситуация:** пассажир считает, что его место занято.

Варианты:

1. **Сверить билет и маркировку, затем проводить к месту** → 2 балла, рост лояльности.
2. **Передать коллеге и взять обязательство проверить результат** → 1 балл + новая задача «Проверить размещение пассажира».
3. **Предложить другое кресло без проверки** → 0 баллов, снижение лояльности и через несколько тактов возможен связанный «Спор из-за пересадки».

Что проверяется: не угадывание ответа, а цена делегирования и последствия непроверенной пересадки.

## Сценарий B — вода у входа

Проблема может быть скрытой и обнаружиться при осмотре.

**Ситуация:** на полу вода, пассажиры обходят мокрый участок.

Варианты:

1. **Обозначить опасное место и организовать уборку с проверкой** → 2 балла + две задачи: убрать воду и затем проверить сухость.
2. **Быстро промокнуть салфетками** → 1 балл, небольшое снижение safety и возможная связанная проблема «Пол всё ещё скользкий».
3. **Продолжить обслуживание и вернуться позже** → 0 баллов, серьёзное снижение safety и loyalty.

Здесь лучший ответ создаёт дополнительную рабочую нагрузку. Если игрок не успеет выполнить уборку/проверку, задачи сами получат отрицательные исходы.

## Сценарий C — громкий разговор

**Ситуация:** пассажир говорит по громкой связи, рядом отдыхают другие люди.

Варианты:

1. **Спокойно договориться о другом формате разговора** → 2 балла.
2. **Попросить говорить тише и позже проверить** → 1 балл + задача «Проверить тишину» + возможное возвращение проблемы.
3. **Предложить соседям потерпеть** → 0 баллов, ухудшение loyalty группы и safety.

Если задача проверки выполнена вовремя, она может предотвратить повторную проблему. Если нет — договорённость может оказаться неустойчивой.

## Сценарий D — просьба о чае и зависимость от штатной задачи

В начале смены есть задача **«Подготовить раздачу напитков»**.

Проблема «Просьба о чае» допускает:

- сразу подать чай из подготовленного запаса — этот вариант доступен только после выполнения подготовки;
- принять заказ и создать задачу «Принести чай»;
- предложить понятную альтернативу;
- ответить неопределённым «позже».

Так штатная обязанность реально изменяет будущие варианты решения, а не существует отдельной декоративной карточкой.

## Сценарий E — пассажиру стало плохо

Критическая ситуация с реальным серверным таймером.

**Первый этап:**

- организовать связь с начальником поезда и помощь → переход к следующему диалогу;
- дать неизвестную таблетку → 0 баллов и фатальная ошибка;
- предложить отдохнуть и уйти → 0 баллов и серьёзные последствия.

**Второй этап после связи:**

- передать место, слова пассажира и наблюдаемые признаки без диагноза → 2 балла + задача проверить дальнейшую помощь;
- сообщить предполагаемый диагноз вместо наблюдаемых фактов → 1 балл;
- прервать связь и оставить пассажира → 0 баллов.

Сценарий проверяет организацию помощи и передачу наблюдаемых фактов, а не медицинское лечение.

## Сценарий F — плед: правильное обещание ещё нужно выполнить

Пассажир просит плед.

Варианты:

- взять задачу принести плед → текущая проблема получает 2 балла;
- предложить частичный компромисс → 1 балл;
- отмахнуться от просьбы → 0 баллов.

Но 2 балла за корректную реакцию **не означают, что работа закончена**: задача «Принести плед» имеет собственный скрытый срок. Если игрок забудет обещание, лояльность позже снизится.

Это демонстрирует ключевую механику продукта: решение ситуации может быть профессионально правильным сейчас и одновременно создавать обязательство, которое надо успеть выполнить позже.

## 14. Почему сценарии нелинейны

Нелинейность возникает не только внутри карточки выбора.

Решение может:

- завершить проблему;
- создать одну или несколько задач;
- отложить связанную проблему;
- предотвратить будущую проблему;
- изменить доступность следующего варианта;
- изменить loyalty / safety;
- потребовать ещё один этап диалога;
- привести к фатальному исходу.

Параллельно живут другие проблемы и внутренние сроки. Поэтому одна и та же библиотека ситуаций даёт разные смены в зависимости от случайного набора, порядка появления, скрытости и решений пользователя.

## 15. Демонстрационный маршрут для жюри

Для короткой демонстрации удобно показать:

1. открыть профиль и запустить orientation или service;
2. начать смену и увидеть приёмку + обслуживание + несколько обращений;
3. сознательно выполнить одну штатную задачу;
4. решить проблему вариантом, создающим новое обязательство;
5. выполнить осмотр и открыть скрытую проблему;
6. показать, что найденные дела остаются в общем списке;
7. открыть карту вагона и лог;
8. закончить смену;
9. показать итог FACT / MAX / 0–100;
10. перейти в профиль и показать рост накопительных очков компетенций и рейтинг.

Для технической демонстрации дополнительно можно показать reload незавершённой смены: состояние восстанавливается с сервера, а критический реальный deadline продолжает контролироваться сервером.


## 16. Уточнение карточек и навигации

Открытую проблему надо довести до результата: карта и лог доступны для чтения, но переключение на другую проблему блокируется. На карте первое нажатие показывает название и описание, затем отдельная кнопка открывает проблему. Задачи сначала показывают описание и кнопку выполнения. Завершённые дела исключаются из списков и остаются в истории. Лог только текущей смены, новые записи сверху, подробности свернуты. Уведомления прежней системы удалены из пользовательского меню.
