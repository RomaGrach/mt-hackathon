# Ограничения решения и план развития после хакатона

РЕЙС 400 закрывает полный игровой цикл MVP: серверная смена, нелинейные ситуации, скрытые проблемы, задачи, критический таймер, шкалы, история, итоговый разбор, накопительные очки компетенций и рейтинг. При этом текущая версия является **учебным конкурсным прототипом на синтетических данных**, а не готовой корпоративной системой аттестации персонала.

Ниже ограничения разделены на продуктовые, методические и технические, чтобы не смешивать то, что уже работает, с тем, что требуется для промышленного внедрения.

## 1. Методические ограничения

### Синтетический контент

Ситуации Design002 разработаны как демонстрационная учебная библиотека по материалам кейса и обсуждениям с экспертами. Они не являются утверждёнными должностными инструкциями перевозчика.

Перед использованием в реальном обучении необходимо:

- провести методическую экспертизу каждой ситуации;
- сверить формулировки с действующими регламентами;
- подтвердить критические действия и недопустимые варианты;
- проверить коэффициенты loyalty / safety;
- проверить сроки проблем и задач;
- проверить длительность критического таймера;
- согласовать итоговую рубрику.

### Очки компетенций не являются кадровой оценкой

Текущий показатель competency points — внутриигровой накопительный прогресс.

Формула прозрачна:

- проблема даёт 0 / 1 / 2;
- shiftScore = FACT / MAX × 100;
- competencyGain завершённой полной смены равен shiftScore;
- накопительный показатель — сумма competencyGain.

Он удобен для обучения и мотивации, но сам по себе не доказывает профессиональную пригодность, не должен использоваться для найма, увольнения, оплаты труда или дисциплинарных решений без отдельной валидизации.

### Нет доказанного переноса навыка

На хакатоне не проведено продольное исследование, показывающее, что высокий игровой результат означает лучшее поведение в реальной поездке. Для этого нужен пилот с целевой аудиторией, pre/post assessment и наблюдение за устойчивостью навыка.

## 2. Ограничения игрового контента

### Ограниченная библиотека

В Design002 есть достаточное число ситуаций для разных комбинаций смен, однако это не производственный каталог всех обязанностей проводника.

Нужны дополнительные пакеты:

- приёмка и подготовка состава;
- сервис по классам;
- конфликтные ситуации;
- безопасность;
- особые категории пассажиров;
- внештатные события;
- взаимодействие с бригадой;
- завершение рейса.

### Баланс ещё требует пилота

Варианты orientation / service / attention / full имеют настроенные квоты и длину 8 / 10 / 16 / 20 тактов. Внутренние сроки проблем и задач уже конечны, но их окончательные значения следует корректировать по данным пилота.

Цель балансировки — не максимизировать сложность, а получить ситуацию, где:

- выполнить всё невозможно;
- профессионально важные приоритеты различимы по содержанию;
- случайность не делает смену заведомо несправедливой;
- разные стратегии дают интерпретируемые последствия.

### Критический таймер общий по политике

Сейчас Design002 использует 60 или 120 секунд для критических сцен. Индивидуальная адаптация времени под доступность, устройство, тип ситуации или специальные потребности пользователя не реализована.

## 3. Авторизация и роли

Текущая учебная сессия рассчитана на демонстрацию:

- нет корпоративного SSO;
- нет MFA;
- нет восстановления аккаунта;
- нет переноса профиля между устройствами;
- нет полноценных ролей «сотрудник / методист / руководитель / администратор»;
- нет RBAC/ABAC.

Публичный тестовый экран администратора сейчас read-only и создан для демонстрации. Он не является производственным контуром администрирования и перед реальным внедрением должен быть закрыт корпоративной авторизацией и аудитом доступа.

## 4. Хранилище и масштабирование

### Текущее состояние

Self-hosted версия использует:

- один Node.js 24 процесс;
- встроенный node:sqlite;
- один локальный файл SQLite;
- WAL;
- foreign keys;
- BEGIN IMMEDIATE;
- busy_timeout;
- синхронный Store API.

Эта архитектура подходит для хакатонного MVP и небольшого односерверного пилота.

### Почему SQLite остаётся в конкурсной версии

Переход на PostgreSQL прямо перед сдачей не является «заменой одной настройки». Сейчас код использует:

- синхронный DatabaseSync;
- SQLite PRAGMA;
- BEGIN IMMEDIATE;
- SQLite JSON-функции;
- SQL, рассчитанный на текущую схему;
- тесты, построенные вокруг текущей транзакционной модели.

Безопасная миграция потребует нового storage adapter, изменения транзакционных блокировок, миграций схемы и повторной проверки retry/revision/concurrency.

Для одного российского сервера, на котором будет работать конкурсный прототип, эти риски превышают пользу от срочной миграции.

### Когда PostgreSQL становится необходим

PostgreSQL следует вводить при появлении хотя бы части следующих требований:

- несколько backend-реплик;
- высокая параллельная нагрузка;
- managed database;
- репликация / HA;
- point-in-time recovery;
- централизованный operational access;
- тяжёлая аналитика;
- интеграционные workers;
- требования заказчика к СУБД.

Игровой движок при этом можно сохранить: он отделён от HTTP и persistence. Основная работа сосредоточится в Store/queries и эксплуатационном контуре.

### SQLite нельзя масштабировать через сетевой shared file

Файл БД не следует размещать на общей сетевой папке между несколькими backend-узлами. Для горизонтального масштабирования нужен настоящий сервер БД.

## 5. Производительность

Нагрузочные испытания уровня производственной эксплуатации не проводились.

Текущий sync SQLite подход означает:

- один процесс сериализует изменяющие транзакции;
- тяжёлый SQL или длительная операция может задержать другие запросы;
- нет отдельной очереди фоновых jobs;
- нет автоматического горизонтального масштабирования.

Для демонстрационного трафика это приемлемо. Для пилота необходимо измерить p50/p95/p99 latency, error rate и конкурентное поведение при реальном количестве пользователей.

## 6. Reverse proxy и rate limit

Сервер по умолчанию ориентирован на localhost за внешним HTTPS reverse proxy.

Текущий rate limiter использует TCP-адрес соединения и намеренно не доверяет X-Forwarded-For. Поэтому при обычной схеме Nginx/Caddy несколько внешних пользователей могут выглядеть приложению как один адрес прокси и делить лимит.

Для production необходимо:

- явно настроить доверенный proxy;
- корректно извлекать реальный адрес только из доверенной цепочки;
- либо использовать общий внешний limiter;
- проверить защиту от spoofed forwarding headers.

Для небольшой конкурсной демонстрации это известное ограничение, а не повод отключать защиту.

## 7. Данные и 152-ФЗ

Демонстрация использует синтетические профили. Юридическая модель работы с реальными сотрудниками отдельно не проходила проверку.

Для production потребуются:

- определённая цель обработки;
- состав реально необходимых данных;
- сроки хранения;
- правила удаления;
- управление доступом;
- журналирование административных действий;
- политика резервных копий;
- согласованное размещение данных;
- ИБ и юридическая экспертиза, включая требования 152-ФЗ.

Сам факт размещения приложения на российском сервере не заменяет эту работу.

## 8. Backup и disaster recovery

Локальный SQLite-файл — единственная постоянная база self-hosted MVP.

Для демонстрации достаточно регулярной резервной копии с корректной процедурой SQLite backup / остановкой процесса.

Для production нужны:

- автоматические backup;
- off-host копии;
- шифрование;
- retention policy;
- регулярная проверка restore;
- RPO/RTO;
- после перехода на PostgreSQL — PITR и контролируемые миграции.

Наличие backup без проверенного восстановления не считается полноценным DR.

## 9. Интеграции

Сейчас есть read-only интеграционный экспорт profiles/results при включённом HR_API_KEY.

Не реализованы:

- подключение к конкретной HR/LMS заказчика;
- SSO;
- SCORM/xAPI;
- webhook/event delivery;
- назначения учебных программ из внешней системы;
- двусторонняя синхронизация;
- жизненный цикл учётной записи сотрудника.

Перед интеграцией необходимо согласовать контракт, идентификаторы, права доступа и семантику результатов.

## 10. Наблюдаемость и эксплуатация

Для промышленного режима не хватает единого production-контура:

- structured logs;
- централизованного сбора ошибок;
- метрик приложения;
- alerting;
- tracing;
- dashboard SLI/SLO;
- автоматизированного release/rollback;
- security scanning в эксплуатационном pipeline.

Health endpoint проверяет процесс и доступ к БД, но сам по себе не является мониторингом системы.

## 11. Безопасность

В MVP уже есть полезные базовые меры:

- HttpOnly session cookie;
- same-origin проверка;
- X-Reis-Client;
- ограничение тела запросов;
- rate limiting;
- read-only Bearer integration;
- серверное вычисление результата;
- idempotent requestId;
- revision;
- immutable content versions.

До production дополнительно нужны:

- SSO/MFA;
- RBAC;
- secrets manager;
- security headers и CSP review;
- dependency scanning;
- pentest;
- аудит reverse proxy;
- ротация и отзыв интеграционных ключей;
- административный audit trail на уровне реальных ролей.

## 12. Совместимость старых версий

Репозиторий сохраняет shift-2 / shift-3 и раннюю gamification-модель, чтобы старые результаты оставались читаемыми.

Это создаёт дополнительную сложность:

- старые XP/СП нельзя складывать с competency points;
- разные engineVersion имеют разные правила;
- аналитика должна учитывать scenarioVersion / engineVersion;
- новые правила не должны пересчитывать историю задним числом.

После пилота можно определить официальную политику архивирования legacy-механик.

# План развития

## Этап 1 — методическая валидизация

Приоритет сразу после хакатона:

1. ревью библиотеки ситуаций заказчиком и экспертами;
2. сверка с регламентами;
3. утверждение критических действий;
4. пользовательские тесты с проводниками/обучающимися;
5. балансировка тактов, внутренних сроков и коэффициентов;
6. проверка понятности итогового разбора.

**Результат:** versioned content pack, который можно обоснованно использовать в пилоте.

## Этап 2 — пилот продукта

1. расширить библиотеку сценариев;
2. добавить назначения курсов;
3. разделить training и formal assessment UX;
4. добавить методический кабинет;
5. добавить доступность и индивидуальные настройки;
6. измерять completion, повторные ошибки и перенос навыков.

**Результат:** управляемый учебный пилот, а не только демонстрационная игра.

## Этап 3 — промышленное хранение и масштабирование

1. реализовать PostgreSQL storage adapter;
2. мигрировать схему и данные;
3. заменить BEGIN IMMEDIATE на корректные row locks / conditional updates;
4. добавить shared rate limiter;
5. вынести фоновые события в очередь;
6. провести concurrency и load tests;
7. настроить backup/PITR.

**Результат:** возможность безопасно запускать несколько backend-реплик.

## Этап 4 — корпоративный контур

1. SSO и RBAC;
2. интеграция HR/LMS;
3. lifecycle пользователей;
4. реальные роли и аудит;
5. ИБ и 152-ФЗ;
6. мониторинг, alerting, release pipeline;
7. формализованные SLO и DR.

**Результат:** техническая основа для производственного пилота у заказчика.

## Этап 5 — доказательство эффективности

1. контрольная группа;
2. pre/post assessment;
3. метрики повторяемости ошибок;
4. анализ retention;
5. связь игрового результата с независимой оценкой навыка;
6. корректировка scoring model по данным.

**Результат:** доказательная база того, какие игровые механики действительно улучшают обучение.

## Что входит в конкурсную версию, а что нет

| Область | Сейчас | После хакатона |
|---|---|---|
| Серверный игровой движок | Да | Развитие |
| Скрытые/связанные ситуации | Да | Расширение контента |
| Критический таймер | Да | Адаптивные политики |
| Лояльность / безопасность | Да | Методическая калибровка |
| Итоговый разбор | Да | Расширенная аналитика |
| Competency progress / рейтинг | Да | Валидизация метрики |
| SQLite single-node | Да | PostgreSQL при масштабировании |
| SSO / RBAC | Нет | Да |
| HR/LMS production integration | Нет | Да |
| Высокая нагрузка / HA | Нет | Да |
| Подтверждённая кадровая валидность | Нет | Требует отдельного исследования |

Текущая версия честно позиционируется как воспроизводимый MVP для демонстрации идеи и архитектуры. План развития не выдаётся за уже реализованные возможности.
