# Карта кода и подготовка к защите

[Главная](../README.md) · [Архитектура](ARCHITECTURE.md) · [API](API-V2.md) · [Проверки](QA.md)

Разработка выполнена с помощью ИИ. Документация и тесты не заменяют понимания решения участниками: перед защитой команда должна самостоятельно пройти игру, изучить код и уметь объяснить ограничения.

## Основные модули

| Файл | Назначение |
|---|---|
| `backend/design002-content.js` | Актуальные ситуации, диалоги, исходы, задачи и баланс |
| `backend/design002-engine.js` | Создание смены, команды, сроки, последствия, журнал и результат |
| `backend/shift-runtime.js` | Выбор движка по версии сохранённого прохождения |
| `backend/shift-service.js` | Публикация контента, владение run, revision, requestId и сохранение |
| `backend/design002-progress.js` | Очки компетенций, уровень, история, ошибки и рейтинги |
| `backend/storage.js` | SQLite-схема и транзакции |
| `backend/http.js` | API, валидация запросов, сессии и статика |
| `src/app.js` | Управление экранами и командами, обновление состояния |
| `src/design002-view.js` | Карточки, список дел, лог, итог и профиль |
| `src/wagon-view.js` | Схема вагона и маркеры событий |
| `src/course.js` | Восемь этапов курса и условия их завершения |
| `tests/` | Проверки текущих и сохранённых старых версий |

## Что показать

1. Вход проводника, курс и свою тренировку.
2. Одновременные проблемы и задачи, осмотр и открытие скрытого события.
3. Несколько реплик внутри одной карточки; альтернативный выбор и другой исход.
4. Схему вагона и лог без раскрытия будущих событий.
5. Критический таймер и сохранение состояния после reload.
6. Итог смены, рост очков профиля и рейтинг.
7. Отдельный read-only экран администратора.

Не обещайте воспроизведение конкретной ситуации при любом новом запуске: состав смены случайный. Для точного разбора используйте историю сохранённой попытки и её закреплённую версию.

## Практикум команды

- Найти правило `points` и эффект одного исхода в контенте; объяснить, как он меняет шкалы и итог.
- Проследить команду от кнопки через API до сохранения результата.
- Объяснить разницу между ходами смены и реальным критическим deadline.
- Показать, почему повтор HTTP-запроса не выполняет действие дважды.
- В отдельной ветке изменить реплику/правило, увеличить версию контента, выполнить `npm run check` и `npm test`. Старые опубликованные snapshots не переписывать.
- Объяснить, какие пункты исходного задания реализованы частично: [матрица](REQUIREMENTS.md).
