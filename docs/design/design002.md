# Design 002 — игровая механика смены проводника

**Статус:** рабочая согласованная спецификация механики  
**Назначение:** зафиксировать решения, принятые в обсуждениях игровой смены и требований к задачам проводника.  
**Граница документа:** описывает механику геймплея внутри смены. Точные коэффициенты, контент конкретных ситуаций и часть балансировочных параметров остаются настраиваемыми и/или открытыми.

---

## 1. Основная идея смены

Игровая смена — это не последовательность независимых вопросов и не список задач, который игрок должен полностью закрыть.

Смена представляет собой ограниченный по времени игровой эпизод, в котором одновременно существуют:

- известные проблемы / ситуации;
- скрытые проблемы, которые ещё нужно обнаружить;
- штатные рабочие задачи;
- задачи, возникшие из предыдущих решений;
- многошаговые обязательства;
- отложенные последствия;
- критические ситуации с реальным таймером;
- показатели пассажиров;
- показатели проводника;
- обязательные шкалы лояльности и безопасности;
- журнал происходящего;
- итоговый разбор всей смены.

Ключевой принцип:

> **Суммарно потенциальной работы в смене должно быть больше, чем игрок физически успевает выполнить.**

Поэтому хороший результат определяется не количеством закрытых проблем, а тем, насколько правильно игрок расставил приоритеты и распорядился ограниченным временем.

Игрок должен осознавать, что часть малозначимых проблем и задач он сознательно не успеет решить.

---


## 2. Время и такты

Мир развивается дискретными **тактами**.

Принято единое правило стоимости действия:

> **Любая задача и один отдельный этап решения проблемы стоят ровно один такт.**

Для проблемы один такт — это один завершённый заход:

1. игрок выбирает проблему;
2. входит в неё;
3. проходит текущий этап и принимает решение;
4. выходит из взаимодействия;
5. проходит один такт.

Если содержательная ситуация требует двух или трёх последовательных этапов, она моделируется цепочкой из двух или трёх проблем / этапов, каждый из которых стоит отдельный такт.

То же правило действует для задач: одна задача = один такт.

### 2.1. Нельзя пропустить такт

Отдельного действия «ждать», «ничего не делать» или «пропустить ход» нет.

Каждый такт игрок обязан выбрать полезное рабочее действие:

- решить известную проблему;
- выполнить задачу;
- осмотреть вагон;
- выполнить другое доступное рабочее действие.

### 2.2. Игрок не видит внутренние сроки

Внутри системы проблема может иметь срок до автоматического исхода, однако игрок **не видит число оставшихся тактов**.

Нет интерфейса вида:

> «Осталось 3 такта».

Игрок должен определять срочность по содержанию ситуации и профессиональному ощущению приоритета.

Аналогично задачи не являются таймерами с обратным отсчётом. У игрока нет задач вида «выполнить через три такта» с отображаемым сроком. Это просто текущие обязательства, которыми он распоряжается наряду с остальной работой.

Пока игрок выполняет одно действие:

- другие проблемы продолжают ждать;
- скрытые проблемы продолжают развиваться;
- могут срабатывать автоматические исходы;
- могут появляться связанные проблемы;
- могут появляться новые задачи;
- мир целиком продвигается на один такт.

---


## 3. Проблемы и библиотека ситуаций

В игре существует заранее описанная библиотека проблемных ситуаций.

Из этой библиотеки генератор смены выбирает конкретные проблемы и размещает их по ходу смены.

У проблемы настраиваются:

- момент / условия появления;
- пассажир, место или зона вагона;
- внутренний уровень серьёзности;
- внутреннее число тактов до автоматического исхода;
- варианты действий;
- условия доступности вариантов;
- разные исходы;
- автоматический худший исход при отсутствии реакции;
- влияние на конкретных пассажиров;
- влияние на лояльность;
- влияние на безопасность;
- создание одной или нескольких задач;
- ссылка на следующую связанную проблему;
- условие появления следующей проблемы в зависимости от исхода текущей;
- при необходимости внутренняя задержка до появления следующей проблемы;
- признак немедленного провала смены для конкретного исхода;
- количество баллов компетенции за каждый исход.

### 3.1. Баллы исхода проблемы

Базовая шкала результата проблемы:

- худший исход — **0 баллов**;
- промежуточный исход, если он предусмотрен, — **1 балл**;
- лучший / правильный исход — **2 балла**.

Если промежуточного варианта нет, проблема может иметь только результаты 0 и 2.

Задачи баллов компетенции не дают.

### 3.2. Внутренние уровни проблем

Для генерации и балансировки используются как минимум категории:

- критические;
- значимые;
- обычные;
- мелкие.

Эти категории **не показываются игроку как готовый приоритет**.

Игрок видит описание происходящего и должен сам определить важность ситуации.

Интерфейс не должен сообщать «критическая проблема» или автоматически сортировать события по истинному приоритету.

---


## 4. Появление проблем и генератор смены

Генератор смены заранее формирует сбалансированный набор событий.

В настройках задаются как минимум:

- длина смены в тактах;
- количество критических проблем;
- количество значимых проблем;
- количество обычных проблем;
- количество мелких проблем;
- количество скрытых проблем, которые потенциально появятся в течение смены.

Набор подбирается так, чтобы смена была содержательно решаемой, но при этом суммарной работы было больше доступного времени. Игрок не должен иметь возможность бездумно закрыть всё подряд.

### 4.1. Ограничение нагрузки

Генератор должен распределять проблемы так, чтобы не создавать бессмысленную перегрузку.

Ключевое жёсткое правило:

> **Одновременно может быть активна только одна критическая проблема.**

Остальные типы проблем могут пересекаться и конкурировать за внимание.

### 4.2. Скрытые проблемы

Количество скрытых проблем, которые могут возникнуть за смену, задаётся заранее при генерации и входит в баланс смены.

Генератор не должен бесконечно добавлять новые скрытые проблемы сверх предусмотренного набора.

Игрок заранее не знает:

- сколько скрытых проблем ещё осталось;
- когда именно они существуют;
- через сколько тактов они автоматически завершатся.

---

## 5. Представление проблем игроку

У игрока есть как минимум два представления текущей ситуации.

### 5.1. Список проблем

На основном экране отображается полный список открытых дел: сверху раздел «Проблемы», ниже «Задачи», включая осмотр. Выполненные дела остаются в логе. По уточнению пользователя от 27 сентября открытая карточка удерживает весь диалог, осмотр или выполнение задачи и результат до бесплатного подтверждения «Окей».

Список сортируется:

> **по порядку появления проблем.**

Сортировка не должна автоматически отражать истинный приоритет.

Интерфейс не решает за игрока задачу профессиональной приоритизации.

### 5.2. Схема вагона

Также существует представление вагона с местами в привычной для железнодорожной схемы компоновке.

Возле места / пассажира, с которым связана известная проблема, отображается маркер, например цветной кружок.

Маркер сообщает, что с данным местом связана проблема, но не обязан сообщать её истинную критичность.

---


## 6. Игнорирование, автоисход и конец смены

У проблемы может быть внутреннее допустимое количество тактов ожидания.

Игрок точный срок не видит.

Если игрок не взаимодействовал с проблемой вовремя, срабатывает заранее настроенный **автоматический худший исход**.

Тяжесть последствий индивидуальна:

- мелкая сервисная проблема может лишь немного снизить лояльность;
- затянувшийся шум может ухудшить лояльность нескольких пассажиров;
- конфликт может серьёзно снизить показатели;
- отдельный критический исход может немедленно завершить смену.

Автоматическое плохое разрешение части мелких проблем является нормальной частью приоритизации: игрок заведомо не должен успевать решить всё.

### 6.1. Что происходит в конце смены

Когда заканчивается последний такт, смена заканчивается немедленно.

Все остающиеся:

- активные известные проблемы;
- скрытые проблемы;
- невыполненные задачи;
- незакрытые обязательства

автоматически закрываются по своим отрицательным / худшим исходам.

После этого рассчитываются итоговые показатели и формируется разбор смены.

---


## 7. Критические проблемы и реальный таймер

Часть проблем работает в критическом режиме.

После входа в такую проблему запускается реальный таймер. Ориентировочное значение — около одной минуты, но точная длительность является настройкой.

За это время игрок проходит предусмотренный критический сценарий.

Если таймер истёк:

- срабатывает настроенный плохой исход;
- применяются последствия этого исхода;
- при необходимости создаются связанные задачи / проблемы;
- смена завершается немедленно только в том случае, если это явно настроено для данного исхода.

Нет единого глобального правила «таймаут = проигрыш».

Также нет отдельного глобального правила вида «Safety = 0 всегда завершает игру», если это специально не закреплено в соответствующей игровой настройке / исходе.

> **Немедленный провал задаётся на уровне конкретной проблемы и конкретного исхода.**

Одновременно может быть активна только одна критическая проблема.

Таким образом существуют две системы времени:

1. **такты смены** — стратегическое распределение внимания;
2. **реальный таймер критической проблемы** — давление непосредственно при принятии решения.

---


## 8. Задачи

Помимо проблем в смене существуют **задачи**.

Задача — рабочее действие или обязательство проводника, которое само по себе не является отдельной проблемной ситуацией.

Примеры:

- принять вагон;
- осмотреть вагон;
- выполнить обслуживание;
- разнести чай;
- принести обещанный предмет;
- вернуться к пассажиру;
- проверить результат;
- выполнить другое обещание, возникшее при решении проблемы.

### 8.1. Стоимость задачи

> **Любая отдельная задача стоит один такт.**

Если по смыслу требуется несколько последовательных действий, это моделируется несколькими задачами, а не задачей стоимостью 2–3 такта.

### 8.2. Как задачи возникают

Задачи могут:

- существовать с начала смены;
- быть регулярными действиями;
- появляться по ходу смены;
- возникать как результат решения проблемы;
- возникать сразу в количестве одной или нескольких задач.

Это создаёт важный стратегический эффект.

Если игрок при решении проблем слишком часто берёт на себя дополнительные обещания и обязательства, у него накапливается всё больше задач. Они занимают будущие такты, и смена постепенно превращается в обслуживание созданной самим игроком рутинной нагрузки.

Таким образом, обещание помощи имеет реальную стоимость будущего времени.

### 8.3. У задач нет видимого таймера

Задача не показывает игроку точное количество тактов до просрочки.

У каждой задачи есть внутренний конечный срок жизни, заданный в её настройках. При его истечении задача закрывается своим отрицательным исходом, исчезает из текущих дел и остаётся в истории. Никакой точный обратный отсчёт игроку не показывается. Задача, созданная решением, получает возможность быть выполненной следующим рабочим действием; само создавшее её действие не расходует это окно.

Игрок видит саму задачу и решает, когда ею заниматься.

### 8.4. Последствия задач

Единого штрафа за невыполненную задачу нет.

Конкретная задача сама определяет последствия:

- изменение лояльности;
- изменение безопасности;
- появление проблемы;
- другое изменение состояния смены.

При завершении смены все оставшиеся задачи автоматически получают свой худший исход.

### 8.5. Очки компетенций

Задачи **не приносят очков компетенций**.

Очки компетенций начисляются только за исходы проблем.

## 9. Осмотр вагона и скрытые проблемы

Не все проблемы сразу появляются в общем списке.

Часть проблем существует **скрыто** и обнаруживается через действие:

> **«Осмотреть вагон».**

Осмотр доступен игроку регулярно: он может выбрать его хоть каждый такт.

Игра не сообщает рекомендуемый интервал и не показывает таймер «пора осматривать вагон». Решение о частоте осмотра является частью профессиональной приоритизации.

### 9.1. Стоимость осмотра

Осмотр занимает один такт.

Специальное правило:

> **Если при осмотре обнаружена проблема, одну найденную проблему можно решить немедленно в рамках того же такта.**

То есть:

**осмотр + немедленное решение одной найденной проблемы = один такт.**

### 9.2. Если найдено несколько проблем

Если в ходе одного осмотра обнаружено несколько проблем:

- одну можно решить немедленно;
- остальные становятся известными;
- они попадают в общий список проблем.

### 9.3. Если осмотр не выполнен

Скрытая проблема может некоторое внутренне заданное число тактов существовать незамеченной.

Игрок этого числа не видит.

После истечения внутреннего срока проблема получает свой худший автоматический исход.

### 9.4. Баланс скрытых проблем

Количество скрытых проблем на всю смену задаётся генератором заранее.

Они являются частью общего рассчитанного баланса смены, а не бесконечным динамическим потоком.

---

## 10. Приёмка вагона и штатные обязанности

Приёмка вагона, подготовка раздачи напитков и другие обычные обязанности реализуются через систему задач.

Уточнение от 27 сентября 2026: приёмка доступна только в начале смены. Если первое завершённое рабочее действие — другое, приёмка закрывается как пропущенная. Чтение, открытие обращения и навигация окно не закрывают. Пропущенная приёмка оставляет отложенный риск; выполнить её задним числом нельзя. Регулярный осмотр вагона остаётся отдельным повторяемым действием.

Их невыполнение не обязано давать немедленный прямой штраф.

Предпочтительная причинная модель:

> **не выполнил рабочую обязанность → не обнаружил или не предотвратил риск → риск продолжил существовать → позже возникла проблема или негативное последствие.**

Например:

1. игрок пропустил приёмку вагона;
2. дефект остался незамеченным;
3. несколько тактов ничего явно не происходит;
4. позже появляется связанная проблема или срабатывает плохой исход.

Это позволяет отражать не только работу с пассажирами, но и штатные профессиональные обязанности проводника.

---


## 11. Продолжение ситуаций и отложенные последствия

Отдельного абстрактного механизма «продолжение той же проблемы» не требуется.

Если ситуация должна иметь следующий этап, автор явно задаёт **следующую связанную проблему**.

Получается длинная содержательная цепочка, части которой разнесены по времени.

### 11.1. Связанная следующая проблема

Для каждого исхода первой проблемы можно настроить:

- закончить ситуацию полностью;
- указать следующую проблему;
- указать другую следующую проблему для другого исхода;
- при необходимости задать внутреннюю задержку до её появления.

Игрок не видит обратный отсчёт до такого появления.

Таким образом, развитие цепочки действительно зависит от решения игрока.

### 11.2. Создание задач

Второй механизм влияния на будущее — создание задач.

Исход проблемы может создать:

- ни одной задачи;
- одну задачу;
- несколько задач.

Каждая задача затем расходует отдельный такт.

Это означает, что выбор игрока меняет не только текст результата, но и будущую нагрузку смены.

---

## 12. Взаимодействие проблем между собой

На текущем уровне отдельная универсальная система «Problem A изменяет Problem B» не требуется.

Если одна ситуация воздействует на несколько пассажиров, это можно описать последствиями **одной** проблемы.

Например, шумный пассажир, которого долго не успокаивали, может снизить лояльность сразу у нескольких окружающих пассажиров.

То есть массовое воздействие:

- не требует создавать отдельную проблему каждому пассажиру;
- остаётся частью исхода исходной ситуации.

Связанные последующие ситуации при необходимости создаются через механизм отложенных последствий.

---


## 13. Лояльность пассажиров

Лояльность — обязательная игровая шкала.

Принята следующая модель:

- лояльность хранится на уровне отдельных пассажиров;
- решения могут повышать или снижать лояльность конкретного пассажира;
- одна ситуация может менять лояльность нескольких пассажиров;
- итоговая лояльность смены считается как **простое среднее значение по пассажирам**.

Конкретные коэффициенты изменения задаются настройками ситуаций и позднее балансируются.

---


## 14. Безопасность

Безопасность — единая общая шкала смены / вагона.

Рабочая шкала и конкретные коэффициенты являются настройками игры.

Основная логика:

- неправильные решения могут уменьшать безопасность;
- пропущенные опасные ситуации могут уменьшать её значительно;
- обычное правильное решение бытовой проблемы не обязано повышать безопасность;
- специальные профилактические задачи могут повышать безопасность.

Это не позволяет компенсировать серьёзное нарушение безопасности большим количеством хорошо решённых мелких бытовых ситуаций.

Немедленный провал **не выводится автоматически из одного общего числового порога**, если такое правило специально не настроено.

Фатальность задаётся на уровне конкретной проблемы / исхода.

---


## 15. Очки компетенций и прогресс профиля

Официальные требования используют термин **«очки компетенций»**, но не задают обязательный перечень отдельных компетенций.

Поэтому отдельная авторская система вида «эмпатия / протокол / скорость / командная работа» в этой модели не используется.

### 15.1. Единый накопительный показатель

> **Очки компетенций — единый накопительный показатель профессионального прогресса проводника.**

Он растёт после каждой завершённой смены и не уменьшается.

### 15.2. Баллы отдельных проблем

Баллы дают только проблемы.

Для каждого исхода проблемы используется базовая шкала:

- худший исход — 0;
- промежуточный исход — 1, если он есть;
- лучший исход — 2.

Задачи баллов компетенций не дают.

Автоматически закрытая по худшему исходу проблема даёт 0 баллов.

### 15.3. Результат конкретной смены

После смены считается максимально возможный результат по всем проблемам, которые вошли в эту смену и фактически учитываются в её итоговом наборе.

Если в смене было N проблем и максимум каждой — 2 балла:

**MAX = N × 2**

Фактический результат:

**FACT = сумма баллов за исходы всех проблем**

Нормированный результат смены:

**SHIFT_SCORE = FACT / MAX × 100**

То есть каждая смена даёт результат от 0 до 100.

В расчёт входят в том числе проблемы, которые:

- были скрыты;
- не были обнаружены;
- закрылись автоматически;
- остались активными до конца смены и получили худший исход.

Таким образом, пропустить проблему нельзя выгодно: она всё равно входит в максимальный возможный результат и при плохом исходе приносит 0.

### 15.4. Накопление

Нормированный результат каждой смены добавляется к общему показателю:

**COMPETENCY_POINTS = сумма SHIFT_SCORE всех завершённых смен**

Например:

- смена 1 — 75;
- смена 2 — 90;
- смена 3 — 62;
- всего — 227 очков компетенций.

Этот показатель всегда растёт по мере прохождения смен.

### 15.5. Рейтинг

Накопленные очки компетенций могут использоваться как основной показатель в рейтинговой таблице.

Это означает, что рейтинг поощряет одновременно:

- качество прохождения;
- регулярность профессиональной практики.

### 15.6. Аналитика пробелов

Отдельные придуманные категории компетенций не вводятся.

Аналитика объясняет прогресс через обязательные измеримые показатели и историю:

- безопасность;
- лояльность;
- конкретные решения;
- типовые ошибки;
- пропущенные проблемы;
- автоматические плохие исходы;
- накопившиеся невыполненные обязательства.

Уровень профиля должен быть связан с накопленными очками компетенций, однако точные пороги уровней являются мета-прогрессом и балансировочной настройкой.

---

## 16. Как оценивается приоритизация

Отдельная абстрактная награда:

> «+10 за правильный приоритет»

не требуется.

Приоритизация проявляется через реальные последствия.

Например:

- игрок решил много мелких задач;
- при этом пропустил опасный конфликт;
- безопасность сильно снизилась;

или:

- игрок сознательно оставил незначительную сервисную просьбу;
- зато вовремя отреагировал на критическую угрозу;
- итоговая смена оценивается лучше.

То есть:

> **ценность результата не равна количеству решённых проблем.**

---

## 17. Лог / история смены

В интерфейсе должна существовать отдельная вкладка:

> **«Лог» / «История смены».**

Это не только технический журнал, а инструмент ситуационной осведомлённости игрока.

После завершения действия результат остаётся внутри его карточки: реакция, изменение показателей и связанные новые обязательства. Кнопка «Окей» возвращает к списку без расхода хода; на последнем действии открывает уже сохранённый итог смены. На общем списке результатов нет. Автоматические события других дел остаются в логе и не подменяют результат выбранного действия. Всплывающие окна не нужны. Будущие и скрытые события заранее не раскрываются. На кнопках и карточках действий не показывается их стоимость «1 ход».

В логе необходимо видеть:

- какие проблемы появлялись;
- когда они появились;
- какие проблемы были обнаружены;
- какие оставались скрытыми;
- когда игрок взаимодействовал с проблемой;
- что он сделал;
- какие задачи возникли;
- какие задачи были выполнены;
- какие задачи были просрочены;
- какие проблемы закрылись автоматически;
- какой автоматический исход сработал;
- насколько серьёзны были последствия;
- когда последний раз выполнялся осмотр;
- когда выполнялись другие регулярные действия;
- какие отложенные последствия сработали;
- как изменялась лояльность;
- как изменялась безопасность;
- какие другие коэффициенты изменились;
- какое конкретное событие вызвало изменение показателя.

Если проблема разрешилась сама, она **не должна бесследно исчезать из интерфейса**.

Её завершение и последствия остаются доступными через историю смены.

---


## 18. Итоговый разбор смены

После окончания смены игрок получает разбор всей сессии.

В нём отражаются:

- возникшие проблемы;
- обнаруженные и необнаруженные проблемы;
- решения игрока;
- автоматические плохие исходы;
- задачи, которые появились;
- выполненные и невыполненные задачи;
- связанные проблемы, появившиеся вследствие решений;
- критические ошибки;
- изменения лояльности;
- изменения безопасности;
- баллы, полученные за каждую проблему;
- максимально возможное количество баллов;
- фактически набранные баллы;
- нормированный результат смены 0–100;
- добавленные накопительные очки компетенций;
- причинно-следственная связь между действиями и последствиями.

Также полезна статистика:

- сколько проблем решено;
- сколько завершилось автоматически;
- сколько осталось скрытыми до плохого исхода;
- сколько задач выполнено;
- сколько задач завершилось отрицательно;
- сколько критических ситуаций провалено.

Итог должен объяснять не только «правильно / неправильно», но и качество распределения внимания в условиях ограниченных тактов.

---


## 19. Как решения меняют дальнейшее течение смены

Влияние решений на будущее реализуется через два основных механизма.

### 19.1. Следующая связанная проблема

Исход одной проблемы может явно указывать следующую проблему.

Разные варианты решения первой проблемы могут:

- завершить цепочку;
- привести к разным следующим проблемам;
- привести к следующему этапу через внутреннюю задержку.

Так получается составная ситуация / длинный диалог, растянутый на несколько тактов.

### 19.2. Создание задач

Исход проблемы может создавать одну или несколько задач.

Поскольку каждая задача требует отдельного такта, решения игрока напрямую меняют будущую загрузку.

Например, стратегия «всем всё пообещать» приводит к накоплению обязательств и расходует всё больше будущих тактов на рутину.

Дополнительно решения продолжают непосредственно менять:

- лояльность пассажиров;
- безопасность;
- итог проблемы;
- баллы компетенций за проблему;
- возможность немедленного провала, если это настроено в исходе.

---

## 20. Связь с требованиями конкурса

При проектировании механики необходимо сохранить обязательные элементы формального задания:

- профиль проводника;
- прогресс;
- уровень;
- очки компетенций;
- нелинейные сценарии;
- условия;
- несколько исходов;
- таймер критических решений;
- шкалу лояльности пассажира;
- рейтинг / шкалу безопасности;
- детальный разбор последствий;
- аналитику действий пользователя;
- аналитику прогресса;
- аналитику пробелов в компетенциях.

Из уточнений экспертов также важно учитывать:

- обнаружение проблем должно входить в само задание;
- игрок не должен получать готовый ответ, какую проблему решать первой;
- одновременно в вагоне может существовать несколько разных ситуаций;
- проводник должен быстро переключаться между ними;
- игровая работа не должна ограничиваться только пассажирскими жалобами;
- существенная часть профессиональной деятельности связана с заступлением, приёмкой поезда и другими штатными обязанностями.

## 21. Сводный игровой цикл

1. Перед началом смены генератор формирует ограниченный и сбалансированный набор проблем, включая скрытые.
2. Настраивается количество проблем разных классов и длина смены.
3. Одновременно допускается не более одной критической проблемы.
4. Часть проблем известна сразу, часть скрыта.
5. Игрок видит список известных проблем и схему вагона.
6. Игрок обязан каждый такт выбрать действие; пропуска хода нет.
7. Любая задача или один этап проблемы стоят один такт.
8. Осмотр также стоит один такт и может включить немедленное решение одной найденной проблемы.
9. Игрок не видит внутренних сроков до автоматических исходов.
10. Пока выполняется действие, весь мир продвигается на такт.
11. Просроченные проблемы получают худшие автоматические исходы.
12. Решение проблемы может явно породить следующую связанную проблему.
13. Решение проблемы может породить одну или несколько задач.
14. Задачи создают будущую нагрузку, но не дают очков компетенций.
15. Проблемы дают 0 / 1 / 2 балла в зависимости от исхода.
16. В конце последнего такта все оставшиеся проблемы и задачи автоматически закрываются по худшим исходам.
17. Итоговая лояльность считается как среднее по пассажирам.
18. Рассчитывается безопасность.
19. Рассчитывается нормированный результат проблем смены от 0 до 100.
20. Этот результат добавляется к накопительным очкам компетенций профиля.
21. Все события и последствия доступны в логе и итоговом разборе.

## Итоговая концепция

На текущем уровне согласована следующая основа:

> **Смена — это система конкурирующих за внимание проблем и рабочих задач, часть которых скрыта, часть имеет сроки, часть порождает отложенные последствия. Мир развивается тактами. Игрок заведомо не может выполнить всё и поэтому должен самостоятельно обнаруживать ситуации, оценивать их важность, переключаться между ними и принимать осмысленные решения о том, чем пожертвовать. Качество работы определяется последствиями для пассажиров, безопасности и профессиональных показателей, а не количеством закрытых карточек.**


## 24. Уточнение пользовательского пути: карточки, 27 сентября 2026

- Обычный запуск с главной — одним нажатием; повторное подтверждение начала убрано. Правила объясняются в обучении.
- Задача открывает описание перед выполнением. Значок открытой задачи не выглядит как галочка завершения. Осмотр находится среди задач; найденные проблемы выбираются внутри его карточки.
- Открытая проблема содержит разговор, промежуточные реакции и дальнейшие решения. Нормальные маршруты содержат несколько выборов; разные реплики ведут к разным продолжениям и исходам. Порядок ответов перемешивается, но стабилен при перезагрузке сцены.
- До завершения проблемы нельзя вернуться к списку или переключить её через карту. Карта и журнал доступны для просмотра. Выход на главную сохраняет открытую проблему; её срочный таймер продолжает идти.
- На карте первое нажатие показывает название и описание известной проблемы, второе открывает её, если текущая карточка завершена.
- Журнал отдельный для каждой смены; последние записи сверху, подробности свернуты. Старые уведомления и их счётчик удалены из пользовательского меню.
- Из итогового числа убрана подпись «/100». После самоисправления в отзыве («45 из 100») формула нормирования из раздела 14 не изменена; накопительные очки остаются суммой результатов смен.
- Подтверждение результата карточки не тратит ход, не выдаёт награду повторно и сохраняется на сервере. Старые закреплённые версии механики не пересчитываются.
