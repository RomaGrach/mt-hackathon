# Архитектура РЕЙС 400

Актуальное состояние для конкурсной сдачи: приложение **2.1**, основной сценарий **design002@1.3.0**, игровой движок **shift-4**, транспортный API **v2**. Старые попытки на shift-2/shift-3 сохранены только для обратной совместимости и не описывают текущий игровой цикл.

Основной вариант развёртывания для сдачи — один Node.js 24 процесс на сервере команды, статический интерфейс и API на одном origin, SQLite как локальное постоянное хранилище. Такая схема намеренно проста для воспроизводимого MVP: сервер остаётся единственным источником истины, а игровая логика отделена от HTTP и слоя хранения.

## 1. Компоненты

~~~mermaid
flowchart LR
  U[Проводник / браузер] -->|HTTPS, JSON, HttpOnly cookie| H[HTTP API<br/>backend/http.js]
  H --> S[Application services<br/>Service + ShiftService]
  S --> R[Runtime dispatcher<br/>shift-runtime.js]
  R --> E4[Design002 engine<br/>shift-4]
  R --> EL[Legacy engines<br/>shift-2 / shift-3]
  S --> C[Versioned content<br/>design002-content.js]
  S --> CP[Competency progress<br/>design002-progress.js]
  S --> M[Legacy motivation<br/>compatibility]
  S --> DB[(Store / SQLite<br/>node:sqlite)]
  CP --> DB
  C --> DB
  H --> O[OpenAPI 3.1<br/>/api/openapi.json]
  I[HR / LMS integration<br/>read-only, optional] -->|Bearer token| H
~~~

### Браузер

Интерфейс не рассчитывает итоговые баллы, не хранит авторитетное состояние смены и не сообщает серверу, сколько времени прошло. Клиент показывает только опубликованное сервером состояние и отправляет выбранную команду с текущей revision и уникальным requestId.

Для shift-4 основной экран объединяет известные проблемы и рабочие задачи в один список «Дела». Дополнительно доступны схема вагона, лог событий, профиль, итоговый разбор и рейтинг по накопительным очкам компетенций.

### HTTP-слой

**backend/http.js** отвечает за:

- сессию через HttpOnly cookie reis_session;
- проверку same-origin и защитного заголовка X-Reis-Client для изменяющих запросов;
- ограничения размера и частоты запросов;
- маршрутизацию API v2;
- выдачу OpenAPI;
- health-check;
- опциональный read-only интеграционный API.

HTTP-обработчики не содержат правил игрового мира.

### Application services

**Service** управляет профилем, сессией, bootstrap и совместимостью старых модулей.

**ShiftService** отвечает за жизненный цикл серверной смены:

- публикацию и выбор версионированного контента;
- создание run;
- проверку владельца попытки;
- идемпотентность requestId;
- optimistic concurrency через revision;
- сохранение checkpoint, журнала и результата;
- серверную обработку истёкшего критического таймера;
- выдачу накопительного прогресса и рейтинга Design002.

### Runtime и движок

**backend/shift-runtime.js** выбирает движок по закреплённому engineVersion. Новые смены Design002 выполняются в **backend/design002-engine.js**.

Движок получает только состояние, версионированный контент, команду и серверное время и возвращает новое состояние. Для shift-4 он реализует:

- конечный заранее сформированный пул проблем;
- известные и скрытые проблемы;
- ограниченное число тактов;
- один такт на отдельное рабочее действие;
- осмотр с обнаружением скрытых проблем;
- возможность решить одну найденную проблему в рамках того же такта осмотра;
- задачи с конечным внутренним сроком;
- связанные последствия и новые задачи;
- критические проблемы с реальным серверным таймером;
- шкалы лояльности и безопасности;
- причинный журнал;
- итог 0–100 и накопительные очки компетенций.

Контент отделён от алгоритма движка. Текущая библиотека и баланс находятся в **backend/design002-content.js**, концептуальные правила — в [design/design002.md](design/design002.md).

### Хранилище

**backend/storage.js** — небольшой адаптер над встроенным Node.js модулем node:sqlite. Доменная логика обращается к Store, а не к файловой системе напрямую.

SQLite настроен с:

- foreign_keys=ON;
- journal_mode=WAL;
- busy_timeout=5000;
- BEGIN IMMEDIATE для изменяющей транзакции.

Версии сценария сохраняются неизменяемо: если документ с уже существующей парой id/version отличается, публикация отклоняется и автор обязан увеличить версию.

## 2. Последовательность одной команды

~~~mermaid
sequenceDiagram
  participant B as Browser
  participant H as HTTP
  participant S as ShiftService
  participant D as SQLite
  participant E as shift-4

  B->>H: POST /api/v2/runs/:id/commands<br/>requestId + revision + command
  H->>H: Session / origin / payload validation
  H->>S: command(profile, runId, body)
  S->>D: BEGIN IMMEDIATE
  S->>D: Find receipt by profile + requestId

  alt Request already accepted
    D-->>S: Saved response
  else New request
    S->>D: Load run + pinned content + hashes
    S->>S: Apply expired critical deadline if needed
    S->>S: Compare revision
    S->>E: reduce(state, command, content, serverNow)
    E-->>S: New authoritative state
    S->>D: Save run, new events, transition, result
    S->>D: Save idempotent response
  end

  S->>D: COMMIT
  S-->>H: receipt + public run
  H-->>B: Authoritative state
~~~

Успешная команда, её журнал, итоговый result и квитанция requestId фиксируются атомарно. Повтор того же запроса с тем же requestId возвращает сохранённый ответ, а повтор с изменённым содержимым получает KEY_REUSED. Старая revision не создаёт второй переход.

## 3. Последовательность игровой смены

~~~mermaid
flowchart TD
  A[Автоматический старт] --> B[Проблемы и задачи]
  B --> C[Диалог или рабочее действие]
  C --> D[Сервер продвигает мир и сохраняет исход]
  D --> E[Игрок читает результат внутри карточки]
  E -->|Окей: без хода| F{Смена завершена?}
  F -->|Нет| B
  F -->|Да| G[Итог и накопленный прогресс]
~~~

Результат последнего действия и начисление сохраняются сервером сразу. Подтверждение карточки управляет переходом интерфейса и не расходует ход; финальный экран открывается после него.

Внутренние сроки проблем и задач игроку не показываются. Срочность оценивается по содержанию. Исключение — уже открытая критическая ситуация: для неё сервер публикует реальный deadline и проверяет его при следующем запросе.

## 4. Данные и версии

Основные базовые таблицы:

| Группа | Таблицы | Назначение |
|---|---|---|
| Профиль и доступ | profiles, sessions | Синтетический профиль и серверная сессия |
| Контент | scenarios, shift_publications | Неизменяемые версии сценариев и активные публикации |
| Попытка | runs, shift_meta | Текущее состояние, версия движка, hashes, initial state |
| Журнал | events, shift_events, shift_transitions | История и воспроизводимые переходы |
| Результаты | results | Единственный итог на run |
| Идемпотентность | requests | Ответ на уже принятую команду по requestId |
| Мотивация legacy | motivation_* / practice_* / competition_* | Сохранённая совместимость ранней модели |

Для Design002 накопительные очки компетенций не требуют отдельной изменяемой «кассы»: профиль рассчитывается по сохранённым shift-4 results. Завершение смены добавляет её нормированный shiftScore к competencyGain, в том числе при фатальном исходе. Пользовательское прерывание и производная попытка с origin дают 0 очков. Уровень профиля рассчитывается по накопленной сумме.

Состояние run и result содержат закреплённые schemaVersion, engineVersion и scenarioVersion. Содержание дополнительно проверяется по content/rules hash, поэтому старая попытка не может незаметно продолжиться на новых правилах.

## 5. Инварианты безопасности и корректности

1. **Сервер — источник истины.** Баллы, шкалы, сроки и скрытые события не принимаются от браузера.
2. **Один активный run на профиль.** Нельзя одновременно изменять несколько попыток одного игрока.
3. **Revision защищает от гонок интерфейса.** Действие применяется только к актуальному состоянию.
4. **requestId защищает от повторной отправки.** Сетевой retry не создаёт второй ход.
5. **Критический deadline серверный.** Поздний выбор не побеждает уже наступивший timeout.
6. **Версия контента закрепляется при старте.** Обновление библиотеки не переписывает старые результаты.
7. **Результат единственный.** results.run_id уникален.
8. **Скрытые знания не выдаются заранее.** Публичная проекция не содержит будущие события и ключи «правильных» ответов.

## 6. Развёртывание на сервере команды

Для конкурсного развёртывания достаточно одного Linux-сервера:

~~~mermaid
flowchart LR
  Internet --> RP[HTTPS reverse proxy<br/>Nginx / Caddy]
  RP -->|127.0.0.1:3000| APP[Node.js 24<br/>РЕЙС 400]
  APP --> DB[(data/reis400.sqlite)]
~~~

Рекомендуемая схема:

- Node.js 24;
- приложение слушает localhost;
- TLS завершается на reverse proxy;
- PUBLIC_ORIGIN указывает публичный HTTPS origin;
- COOKIE_SECURE=true;
- каталог data находится на постоянном диске и резервируется;
- фронтенд и API доступны через один origin.

Dockerfile и compose.yaml остаются воспроизводимым локальным/серверным вариантом запуска. Основной конкурсный URL — **https://5.42.113.212:9443/**. Владелец перенёс туда игру; health подтверждает `shift-4` и SQLite. Конфигурация процесса/reverse proxy и точный deployed SHA отдельно не проверены. [Инструкция развёртывания и границы проверки](DEPLOYMENT.md).

Альтернативный Sites использует `worker/`, SQL.js и snapshot в D1, с отдельной базой и публикацией. Его инструкция сохранена в [SITES-DEPLOYMENT.md](SITES-DEPLOYMENT.md); это не основное размещение для сдачи.

## 7. Почему в release candidate остаётся SQLite

Для текущего MVP SQLite — сознательный выбор, а не заявление о готовности к корпоративной нагрузке. При одной backend-реплике он даёт меньше инфраструктурных точек отказа, не требует отдельного сервиса БД и уже покрыт тестами транзакций, replay, reload и persistence.

Замена на PostgreSQL перед сдачей затронула бы не только connection string: текущий Store синхронный, использует Node DatabaseSync, SQLite JSON-функции, PRAGMA и BEGIN IMMEDIATE. Нужны новый адаптер, другой механизм транзакционных блокировок и повторный полный набор конкурентных тестов.

Поэтому PostgreSQL — следующий инфраструктурный этап, когда появляются несколько backend-реплик, высокая параллельность, централизованные backup/HA и эксплуатационные требования. Этот переход описан в [LIMITATIONS.md](LIMITATIONS.md), но не входит в рискованный feature change финального хакатонного релиза.

## 8. Масштабирование после MVP

Переход к нескольким backend-репликам предполагает:

- PostgreSQL вместо локального SQLite-файла;
- асинхронный storage adapter;
- row-level locking или conditional UPDATE по revision;
- общий rate limiter;
- централизованные логи и метрики;
- фоновые jobs вне процесса приложения;
- backup/PITR и регулярную проверку восстановления;
- нагрузочные и конкурентные тесты.

Движок shift-4 при этом не требуется переписывать: он уже отделён от HTTP и хранилища и работает как детерминированный переход состояния.
