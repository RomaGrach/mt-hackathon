# API v2 — текущий серверный контракт РЕЙС 400

Этот документ описывает актуальный API конкурсной версии. Основной новый игровой сценарий — **design002@1.3.0**, движок — **shift-4**, версия приложения — **2.1**. OpenAPI 3.1 является машиночитаемым контрактом: [openapi.json](openapi.json). Старые shift-2/shift-3 остаются читаемыми для совместимости с ранее сохранёнными попытками, но не являются текущей игровой механикой.

## 1. Базовые принципы

- API и интерфейс работают на одном origin.
- Игрок получает HttpOnly-сессию reis_session.
- Изменяющие запросы требуют Content-Type: application/json и заголовок X-Reis-Client: web.
- Сервер проверяет Origin / Sec-Fetch-Site и не принимает кросс-сайтовое изменение состояния.
- Игровые баллы, таймеры, скрытые события и итоговые шкалы никогда не принимаются от клиента.
- Каждая изменяющая игровая команда использует уникальный requestId и текущую revision.
- Сетевой повтор того же запроса безопасен: сервер хранит идемпотентную квитанцию.
- Попытка другого профиля не раскрывается: сервер отвечает как на отсутствующий ресурс.

## 2. Служебные endpoints

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/health | Health-check приложения и SQLite |
| GET | /api/openapi.json | OpenAPI 3.1 |
| POST | /api/session | Создать синтетический учебный профиль / сессию |
| GET | /api/bootstrap | Профиль, активная попытка, каталог и данные интерфейса |

Пример создания учебной сессии:

~~~http
POST /api/session
Content-Type: application/json
X-Reis-Client: web

{}
~~~

Профили демонстрационные. Реальные кадровые данные для хакатонного запуска не требуются.

## 3. Каталог смен

~~~http
GET /api/v2/catalog
~~~

Ответ содержит опубликованные сценарии без скрытого графа решений:

- id и version;
- engineVersion;
- классы обслуживания;
- доступные политики критического таймера;
- учебные варианты;
- число тактов;
- reviewStatus.

Для текущего Design002:

| Параметр | Значения |
|---|---|
| scenarioId | design002 |
| engineVersion | shift-4 |
| contentVersion | 1.3.0 |
| serviceClass | standard / comfort / business / first |
| timingPolicyId | standard / extended |
| критический таймер | 60 / 120 секунд |
| variantId | orientation / service / attention / full |
| длина вариантов | 8 / 10 / 16 / 20 тактов |

У shift-4 нет режима без критического таймера: обе опубликованные политики имеют положительную реальную длительность.

## 4. Создание смены

~~~http
POST /api/v2/runs
~~~

Пример:

~~~json
{
  "requestId": "1d0c45d7-demo-start",
  "scenarioId": "design002",
  "mode": "training",
  "timingPolicyId": "standard",
  "serviceClass": "standard",
  "variantId": "full"
}
~~~

Допустимые mode: training и assessment.

Если variantId не указан для Design002, сервер использует orientation. Набор конкретных проблем внутри варианта всё равно генерируется сервером на основании id попытки. Игрок не передаёт список ситуаций и не может назначить себе правильные ответы.

У одного профиля может быть только одна незавершённая попытка.

Ответ 201 — публичное состояние ShiftPublic в фазе briefing. Обычный интерфейс сразу отправляет begin в рамках одного пользовательского нажатия; отдельного экрана подтверждения нет.

## 5. Чтение смены

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/v2/runs/:id | Актуальное публичное состояние |
| GET | /api/v2/runs/:id/result | Итог завершённой смены |
| GET | /api/v2/runs/:id/replay | Проверка детерминированного воспроизведения |

GET состояния также применяет уже наступивший критический timeout до формирования ответа. Поэтому перезагрузка страницы не позволяет «заморозить» срочную ситуацию.

Для shift-4 GET replay проверяет, что сохранённые переходы воспроизводят тот же результат. Создание новой ветки через POST replay для Design002 намеренно не используется: пользователь запускает новую полноценную смену.

## 6. Команды

~~~http
POST /api/v2/runs/:id/commands
~~~

Оболочка запроса:

~~~json
{
  "requestId": "f56e40b4-demo-action",
  "revision": 3,
  "command": {
    "type": "task",
    "taskId": "t2"
  }
}
~~~

Для **shift-4** используются следующие команды:

| type | Дополнительные поля | Тратит такт |
|---|---|---:|
| begin | — | нет |
| focus | incidentId | нет |
| overview | — | только закреплённые прежние версии; в открытой карточке 1.3.0 не предлагается |
| choose | incidentId, sceneId, actionId, windowId | да, когда завершает этап проблемы |
| task | taskId | да |
| inspect | zoneId, actionId | да, после завершения осмотра |
| continue | — | бесплатно подтверждает acknowledgement; один такт только при завершении осмотра без решения |
| abort | — | завершает попытку без начисления competencyGain |

Команд wait, pause, resume и hint в текущем shift-4 игровом цикле нет.

Клиент не должен конструировать доступность действий самостоятельно. Сервер публикует run.actions; интерфейс отправляет только одно из актуально предложенных действий.

### Осмотр

Если inspect не находит новых проблем, такт завершается сразу.

Если осмотр обнаружил несколько скрытых проблем, они становятся известными, но такт ещё не продвинут. Игрок может:

- решить **одну** из найденных проблем — решение завершит тот же такт осмотра;
- либо отправить continue и закончить осмотр без немедленного решения.

Остальные найденные проблемы остаются в общем списке дел.

## 7. Revision и идемпотентность

ShiftRun имеет целую revision, увеличивающуюся после принятой команды.

Алгоритм изменяющего запроса:

1. сервер начинает BEGIN IMMEDIATE;
2. ищет сохранённый ответ по profileId + requestId;
3. если точный запрос уже исполнялся — возвращает сохранённый ответ;
4. загружает run и закреплённую версию контента;
5. применяет наступивший критический timeout;
6. сверяет revision;
7. выполняет команду движком;
8. атомарно сохраняет state, события, transition, result и ответ requestId;
9. фиксирует транзакцию.

Основные ошибки:

| Код | Смысл |
|---|---|
| KEY_REUSED | requestId повторно использован с другим содержимым |
| STALE_REVISION | клиент действует по старому состоянию |
| DEADLINE_EXPIRED | критический deadline уже наступил; поздняя команда не выполнена |
| ACTION_NOT_AVAILABLE | действие сейчас не разрешено |
| ACTIVE_RUN | у профиля уже есть незавершённая попытка |
| CONTENT_VERSION_MISSING | закреплённая версия сценария недоступна |
| CONTENT_INTEGRITY | сохранённый hash контента не совпал |
| UNSUPPORTED_RUN_VERSION | движок этой сохранённой попытки не поддержан текущим runtime |

При DEADLINE_EXPIRED ответ может включать уже обновлённый run после серверного timeout.

## 8. Критический таймер

Критическое окно создаётся, когда игрок открывает критическую проблему через focus.

Сервер хранит абсолютный deadline:

- standard — 60 секунд;
- extended — 120 секунд.

Deadline сравнивается с серверным временем до принятия следующей команды. Поздний выбор не применяется даже при правильном actionId.

Истечение таймера запускает худший исход конкретной проблемы. Сам timeout не означает автоматически немедленный проигрыш всей смены: фатальность задаётся конкретным исходом.

## 9. Что возвращает публичное состояние Design002

Публичная проекция shift-4 содержит только сведения, которые уже может знать игрок:

- schemaVersion / engineVersion;
- id попытки;
- scenarioId и contentVersion;
- revision;
- mode / variant / timingPolicy;
- класс и компоновку вагона;
- использованные и доступные такты;
- loyalty / safety;
- известных пассажиров и места;
- известные открытые проблемы;
- рабочие задачи;
- опубликованный criticalWindow;
- доступные actions;
- видимый лог;
- result после завершения;
- acknowledgement — сохраняемый результат открытой карточки до подтверждения;
- serverNow.

Не публикуются заранее:

- скрытые неоткрытые проблемы;
- внутренние сроки в тактах;
- будущие связанные события;
- ключ «правильного» варианта;
- внутренние flags;
- генератор и полный граф последствий.

## 10. Итог Design002

После окончания последнего такта сервер закрывает все оставшиеся активные/запланированные проблемы и задачи их худшими исходами, после чего формирует один Result на run.

Главные поля результата:

| Поле | Значение |
|---|---|
| fact | сумма баллов проблем |
| max | максимум: 2 × число учитываемых проблем |
| shiftScore / episodePoints | fact / max × 100 |
| competencyGain | добавка к накопительному прогрессу |
| scales | итоговые loyalty и safety |
| criticalErrors | критические проблемы с исходом 0 |
| problems | все учитываемые проблемы с исходом, выбором и альтернативой |
| tasks | выполненные и проваленные обязательства |
| history | причинный журнал |
| stats | resolved / automatic / undiscovered / tasksDone / tasksMissed / criticalFailed |

У проблемы базовая шкала 0 / 1 / 2. **Задачи не дают очки компетенций напрямую.**

Для обычной завершённой полной смены:

**competencyGain = shiftScore**

Для abort и учебной ветки origin начисление равно 0.

Критическая ошибка отражается отдельно и не исчезает из разбора даже при хорошем среднем балле.

## 11. Накопительный прогресс и рейтинг

Текущий профиль Design002 доступен через bootstrap и рассчитывается по сохранённым shift-4 results.

Основная логика:

**COMPETENCY_POINTS = сумма competencyGain завершённых shift-4 смен**

Уровень:

**LEVEL = floor(COMPETENCY_POINTS / 250) + 1**

Рейтинг:

~~~http
GET /api/v2/competency/leaderboard?scope=company&offset=0&limit=50
~~~

Допустимые scope:

- crew;
- depot;
- company.

Ответ содержит score, completed, rank и признак me. Равные score получают одинаковый rank.

Это отдельная текущая система прогресса Design002. Старые XP/СП из gamification-1 не суммируются с очками компетенций.

## 12. Старые мотивационные endpoints

В API v2 сохранены endpoints ранней gamification-модели:

- GET /api/v2/motivation;
- POST /api/v2/motivation/preferences;
- POST /api/v2/periods/:periodId/entry;
- POST /api/v2/results/:id/debrief-ack;

Они нужны для чтения старых профилей/попыток и обратной совместимости интерфейса. Для shift-4 очки компетенций записываются при завершении смены; debrief-ack не создаёт вторую награду и возвращает alreadyRecorded.

## 13. Интеграционный API

При заданном HR_API_KEY доступны read-only endpoints:

- GET /api/integrations/v1/profiles;
- GET /api/integrations/v1/results.

Они используют Bearer token и не позволяют внешней системе менять игру или начислять баллы. Полноценная корпоративная SSO/HR-интеграция в MVP не реализована.

## 14. OpenAPI

Файл [openapi.json](openapi.json) генерируется из **scripts/openapi-v2.js**. В нём уже описаны:

- создание и чтение v2 runs;
- command union, включая task;
- Design002Public;
- Design002Result;
- endpoint competency leaderboard;
- legacy v2 contracts.

Если API меняется, сначала обновляется генератор, затем выполняется генерация и проверка, чтобы Markdown и OpenAPI не расходились.


### Карточки 1.3.0

`interactionVersion: 1` запрещает переключение открытого диалога: в scene разрешены choose текущей проблемы и abort. После завершённого действия phase=acknowledgement, предлагается только continue. На последнем ходе phase=result и result сохраняется сразу, но acknowledgement остаётся до continue; подтверждение не меняет баллы/ходы/лог и безопасно повторяется по requestId. Выборы перемешаны стабильно по seed/проблеме/узлу. Локальное открытие описания задачи и предварительный просмотр карты не являются командами исполнения.
