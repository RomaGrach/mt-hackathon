# Развёртывание «РЕЙС 400» в ChatGPT Sites

## Текущее состояние

- Рабочая игра: https://mt-hackathon.realeurguy.chatgpt.site
- Sites `project_id`: `appgprj_6ab65220b22c8191bc605de177134df6`. Этот же ID записан в `.openai/hosting.json`; повторно создавать Site нельзя.
- Аудитория существующего сайта — публичная. Тестовый адрес предназначен для личной игры, а не для передачи жюри.
- Игровой API работает внутри Cloudflare Worker, прикреплённого к Sites. Прогресс хранится в D1, логическое имя привязки — `DB`. Внешний Node/Caddy-сервер для этого развёртывания не требуется.
- Последняя проверенная публикация на момент записи: версия Sites 8, исходный commit Sites `6bba36e2ed5bdbc0987c6b1cc71dda7934739de5` (26 сентября 2026). При следующем выпуске смотрите фактическую последнюю версию в Sites.

Основной GitHub-репозиторий содержит игровой код и инструкцию. У Sites есть **отдельный репозиторий исходников**: изменение GitHub `main` само по себе не обновляет опубликованный сайт. Перед выпуском перенесите изменения из GitHub в checkout *этого же* Site, сохранив его `.git`, проверьте diff и отправьте точное состояние через Sites workflow. Не смешивайте репозитории и не подменяйте `project_id`.

## Что исполняется на сервере

`npm run build:sites` сначала собирает веб-интерфейс, затем создаёт `dist/server/index.js`. Worker раздаёт собранные файлы и `/api/openapi.json`; остальные `/api/*` обслуживает исходный `backend/http.js`, `Service`, `ShiftService`, движок и начисление баллов. Тот же игровой код запускается локально через `node server.mjs` с обычным файлом SQLite.

На каждый запрос Worker загружает сжатый образ SQLite из D1 `game_snapshot`, исполняет команду игры в SQL.js и сохраняет новый образ с проверкой `revision`. При конфликте параллельных запросов он заново читает выигравшую версию и повторяет операцию **до отправки ответа**. Так сохраняются и квитанции `requestId`, и таймеры, и начисление опыта. База внутри отдельного Worker-запроса не считается постоянным хранилищем.

Миграции `drizzle/0000_reis_sessions.sql`, `0001_game_snapshot.sql`, `0002_remove_legacy_sessions.sql` применяются по журналу при публикации. Последняя миграция удаляет только старые тестовые сессии v1; **не выполняйте её повторно как ручной сброс** и не удаляйте `game_snapshot` при обычном обновлении. На рабочей базе остаётся таблица `game_snapshot`.

## Подготовка изменения

Нужен Node.js 24 и установленный плагин Sites с доступом к выбранному проекту.

```sh
npm ci
npm run check
npm run validate:scenarios
npm run validate:shift
npm run format:check
npm test
npm run build:sites
```

`dist/server/index.js` и `dist/.openai/hosting.json` — результаты сборки. Не копируйте в GitHub и Sites `node_modules`, `.env`, SQLite-файлы, архивы развёртывания и личные данные. При изменении структуры D1 сначала добавьте **новую** SQL-миграцию и запись в `drizzle/meta/_journal.json`; не переписывайте уже применённые миграции. Код в `db/schema.ts` и snapshot метаданные должны соответствовать новой схеме.

Сборка адаптирует `sql.js/dist/sql-asm.js` к Worker. В Workers совместимость с Node выставляет `process.versions.node`, а сам SQL.js ошибочно пытается загрузить `node:fs`; кроме того, у Worker может отсутствовать `self.location.href`. Плагин в `scripts/build-sites.mjs` меняет обе ветки определения среды перед bundling. Если версия SQL.js изменилась, проверьте эти выражения и работу реального `/api/bootstrap` после выпуска. В `backend/http.js` вычисление пути через `import.meta.url` должно оставаться внутри ветки раздачи локальных файлов, а не выполняться при загрузке Worker-модуля.

## Как обновить опубликованный сайт

1. Узнайте текущую аудиторию и состояние через Sites `get_site`, сверив ID с `.openai/hosting.json`. Для существующего проекта откройте исходники посредством `site-workflow.mjs` без `archivePath`. Если checkout уже открыт в текущей сессии, используйте его.
2. Перенесите утверждённые изменения из GitHub в checkout исходников Site, **сохраняя его `.git`**. Проверьте, что на месте Worker, миграции, `.openai/hosting.json`, `package.json`, lockfile и нужные файлы приложения. Не переписывайте случайно личные документы, которых нет в рабочем Site.
3. Получите краткоживущий credential через Sites `create_source_repository_write_credential`. Передавайте token только в закрытый stdin `site-workflow.mjs`; не помещайте его в файл, командную строку, коммит, документацию или вывод.
4. Запустите скрипт из checkout Site: `node <sites-plugin-root>/scripts/site-workflow.mjs --project-id appgprj_6ab65220b22c8191bc605de177134df6` с `tty: true`. После приглашения передайте одним JSON-объектом `credential`, прежний `source` (его `project_id` и `checkout_path`), `commands` (`npm ci` при изменённых зависимостях, затем проверки и `npm run build:sites`) и абсолютный `archivePath`. Скрипт сам отправляет исходники и возвращает проверенный `commit_sha` и путь к архиву. Не собирайте архив из другого коммита.
5. Вызовите Sites `save_site_version` с точными `project_id`, `commit_sha` и архивом из предыдущего шага. Затем вызовите `deploy_site_version` с **ID сохранённой версии**. Для этого публичного сайта не переключайте аудиторию на private. Если статус ещё не `succeeded`, проверяйте `get_deployment_status` по ID развёртывания. Предыдущие сохранённые версии доступны для повторного выпуска; откат Worker-кода не откатывает миграции или игровые данные D1.
6. Проверьте опубликованный URL. При ошибке запросов начните с Sites `get_site_worker_logs` (`errors_only=true`); затем проверьте миграции через `read_database_overview`. Не делайте вывод об исправности API по одному статусу «deployment succeeded»: прежняя сборка публиковалась успешно, хотя `/api/bootstrap` отвечал 503.

## Минимальная приёмка после выпуска

- `/api/health` отвечает успешно, `/api/openapi.json` отдаёт документ; путь к исходным серверным файлам не раздаётся как статика.
- Новый профиль создаётся, смена начинается и возобновляется после обновления страницы.
- Приёмка, обращения пассажиров, осмотр вагона, отложенное подтверждение коллеги, адресный возврат и итоговый причинный разбор исполняются через сервер.
- Отметка разбора начисляет XP один раз; после обновления страницы XP и история результата остаются. Проверьте также критический таймер и истечение срока после ухода со страницы, если менялась логика времени.
- На узком экране элементы читаются и доступны; ошибки в консоли и журналах Worker отсутствуют.

26 сентября 2026 на живом сайте пройдена смена класса «Стандарт» до результата 70/70 и 20 XP. После обновления страницы профиль и XP сохранились; после миграции в D1 осталась только `game_snapshot`. Это проверка конкретного маршрута, а не всех развилок.

## Известное ограничение

D1 ограничивает размер одного значения/строки примерно 2 МБ. Worker останавливает запись, когда сжатый образ всей базы достигает 1,9 МБ, и отвечает 503 вместо ложного подтверждения. Эта архитектура подходит для небольшого личного теста; перед длительным использованием или многими игроками перенесите сущности в отдельные записи D1 либо другой постоянный адаптер. Не сбрасывайте действующие результаты молча. `HR_API_KEY` для этой игры не требуется.

## Обновление интерфейса и открытый тестовый администратор — 26 сентября 2026

- На первом экране доступны «Игрок» и «Администратор»; сводка также открывается через меню и `/#admin`.
- По прямому требованию владельца теста администратор общедоступен: нет авторизации, allowlist или `ADMIN_EMAILS`. Это роль просмотра, а не управления сервером.
- `GET /api/admin/users?offset=0` возвращает по 50 учебных профилей: псевдоним, бригаду, статус последнего прохождения, количество попыток/завершений, XP, показатели и последнее действие. Токены, cookie и полные состояния не возвращаются. `GET /api/admin/access` описывает открытый тестовый режим. POST не поддерживается. Реализация одинакова в Node и Sites Worker.
- Таблица обновляется вручную. Последняя активность не означает присутствие онлайн.
- Удалён фоновый GET каждые четыре секунды. Ответ команды обновляет игру; GET нужен при открытии/возврате во вкладку, истечении критического срока и восстановлении сети/неопределённого ответа. Локальная отрисовка секунд не обращается к API.
- Во время запроса блокируются элементы управления без промежуточной перерисовки страницы. Убраны всплывающий индикатор проверки и автоматическая панель напоминаний. В игре нет принудительной прокрутки вверх после действия.
- Компактная закреплённая панель показывает часы, лояльность, безопасность и отдельный критический таймер. Дела разделены в боковой панели; неизвестное дело не раскрывается до осмотра. Разборы свёрнуты.
- Новые ShiftRun используют сохранённый `clockMode: elapsed` и `simulationSeconds`. Старт часов — 08:00. Осмотр занимает 60 с, ожидание 30 с, подтверждение/обещание 30 с, запрос коллеге 45 с, остальные рабочие решения 45 с, пропуск приёмки 15 с. Переходы/чтение — 0 с. Кнопки получают длительности от сервера.
- В текущей смене можно дать одно обещание вернуться к пассажиру: срок — пять игровых минут после действия, просрочка начисляется один раз; повторное обещание не продлевает срок. Ответ коллеги приходит через минуту игрового времени. Критическое окно по-прежнему использует серверное реальное время.
- Старые сохранённые прохождения продолжают прежнюю временную модель; новая применяется к новым прохождениям. Legacy-тесты явно фиксируют старую модель. Новые проверки покрывают прохождение с часами, точное воспроизведение, конечный срок обещания и открытый read-only admin API.
- Приложение устанавливает только host-only `reis_session`, без `Domain`. `__cf_bm` не создаётся и не проксируется прикладным кодом. Настройки Cloudflare cookie не доступны через Sites: предупреждение о домене не объявляется исправленным. Если оно сохраняется, нужна проверка заголовка Set-Cookie и домена со стороны платформы. Удаление polling сокращает повторяющиеся обращения, но не меняет cookie платформы.

Проверки этой ревизии: `npm run check`, `npm test` (95 тестов), `npm run build:sites`. Browser QA в этой среде не выполнен: Worker ESM не имеет совместимого managed dev preview. Это ограничение проверки внешнего вида, не основание заявлять о браузерной проверке.

### Версия 13: публикация контента без повторной работы на каждом запросе

`worker/sites-game.js` сравнивает hash встроенного v1/v2 контента с `runtime_metadata.publication_fingerprint`. Отпечаток записывается только после успешного `createApp` с полной публикацией. Не задавать `publishContent: false` для новой пустой базы: этот флаг применяется только при совпавшем отпечатке. При обновлении содержимого новый hash автоматически запускает прежнюю проверку неизменяемости версий. Внешняя D1-миграция не требуется; старые snapshots обновляются при первом запросе, с прежним CAS.

Игровые вкладки теперь `data-game-tab`/`data-game-pane`, не `data-open-sheet`. Шаги вводного обучения локальны, предпочтение завершения хранится в `reis400.interface-tour.v1` на устройстве. Основной сценарий полностью серверный.
