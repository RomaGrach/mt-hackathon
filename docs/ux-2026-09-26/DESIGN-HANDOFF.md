# Дизайн-поставка и интеграция

## Решение после отзыва 26.09.2026

Пользователь принял направление UX, User Flow и модель обзора с параллельными ситуациями. Условия завершения дизайн-поставки: упрощённая мобильная главная, проверка/обоснование палитры, отдельная поставка дизайна. Эти условия отражены в текущей ревизии; дизайн служит основой реализации #26. Это не разрешение на merge PR, не приёмка runtime и не замена пользовательских испытаний.

## Поставка A — дизайн, ветка ux-review

Весь diff ограничен `docs/ux-2026-09-26/`: документы, User Flow, изолированный HTML-прототип, его локальный файловый просмотрщик, PNG и доказательства проверок. `prototype.js` содержит демонстрационное состояние для кликов; это дизайн-артефакт, не production-движок.

Главная теперь показывает один основной CTA «Начать учебный рейс» / «Продолжить рейс». Цель недели, прогресс и точечная практика доступны через закрытый по умолчанию блок «Другие возможности». Подписанная навигация остаётся доступной. Обзор и игровой экран не переработаны заново.

Палитра сохранена как обоснованное продуктовое решение, не официальная палитра перевозчика. Основание и альтернативы — [DESIGN-SYSTEM](DESIGN-SYSTEM.md#статус-и-обоснование-палитры).

## Поставка B — implementation, задача #26

Рабочие `src/`, корневые `index.html` / `styles.css`, backend, API, SQLite, сборка `dist`, Docker и deployment сюда не входят. Их изменения интегрируются отдельной поставкой вместе с #26 после согласования дизайн-базы.

В PR [#29](https://github.com/RomaGrach/mt-hackathon/pull/29) дизайн смешан с изменениями runtime. Он остаётся открытым без слияния. Его реализацию нельзя принять автоматически вместе с этими документами. Не требуется удалять сделанную работу: переносить нужные части пофайлово/отдельными коммитами с проверкой зависимостей в интеграционную ветку #26, а не cherry-pick всего смешанного PR.

### Условия интеграции #26

1. Реальные PublicRun/команды вместо локального состояния прототипа; скрытые дела не раскрываются через API.
2. Серверные deadline, пауза, requestId/revision, восстановление и защита от повторов. Preview-таймер не считается реализацией этих гарантий.
3. Один результат ShiftRun, независимые Incident/Task, запрос → принятие → исполнение и адресный возврат.
4. Раздельные критерии, XP, СП; миграция и сохранение v1; правила GAMEPLAY и GAMIFICATION-RULES.
5. Контрактные и end-to-end проверки, мобильные состояния/ошибки, реальные пользовательские проверки и проверка на телефоне.
6. Отдельное решение о готовности интеграционного PR. Утверждение дизайна не разрешает слияние #29 и не закрывает #24 целиком.

## Ревью

Принимать отдельно: структуру экранов, микротекст, визуальную иерархию, токены и демонстрационные переходы. Не принимать по этим макетам: защищённые результаты, награды, серверное время, backend, клиническую/профессиональную валидность или выпуск продукта.
