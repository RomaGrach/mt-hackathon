# РЕЙС 400 — UX для согласования

**Результат:** аудит текущего приложения, User Flow, кликабельная концепция, восемь desktop/mobile макетов, дополнительные состояния и базовая дизайн-система. Рабочие `src/`, `styles.css`, backend и данные не изменены. Это отдельный прототип для обсуждения, не новая реализация игры.

## Ветка для согласования

**После отзыва 26.09:** мобильная главная упрощена до одного основного входа и раскрываемого блока вторичных возможностей. [Обоснование палитры](DESIGN-SYSTEM.md#статус-и-обоснование-палитры) и [граница дизайн / implementation #26](DESIGN-HANDOFF.md) оформлены отдельно. Принятое направление используется как дизайн-база; слияние PR и готовность runtime этим не подтверждаются.

Материалы находятся в ветке **`ux-review`**. Чтобы открыть их в существующем клоне репозитория:

```powershell
git fetch origin
git switch ux-review
node docs/ux-2026-09-26/preview.mjs
```

После запуска открыть **http://127.0.0.1:4311**. Установка зависимостей и запуск основного приложения не требуются. Быстрый просмотр без запуска: листы desktop/mobile ниже.

Для согласования проверить понятность перехода обзор → инцидент → результат → обзор; сохранение параллельных дел и обещаний; различие передачи и завершения; мобильные отступы и доступность кнопок; срочное окно и паузу. Замечания удобнее записывать как «экран → действие → что непонятно → предложение».

## Как смотреть

1. Начать с экрана рейса в обзоре; переключить Desktop/Mobile.
2. Открыть багаж, выбрать действие, прочитать результат, вернуться к общей обстановке. Второе дело и обещание сохраняются.
3. Нажать «Пройти с начала» и выполнить маршрут из [User Flow](USER-FLOW.md).
4. Через переключатель посмотреть критический сигнал, паузу, timeout и потерю ответа.
5. Сопоставить аудит и основную концепцию на соседних вкладках обзора.

Переключатель макетов намеренно открывает подготовленные демонстрационные состояния. Полное прохождение ведёт локальное состояние отдельно. Демонстрационные очки и участники в профиле/рейтинге не являются данными реального сервиса.

## Главное изменение

**Одна учебная смена, несколько сохраняющихся дел, один инцидент в фокусе.** Явные названия навигации, короткая общая обстановка, действия рядом с контекстом, две видимые шкалы, отдельное адресное обещание и три стадии передачи коллеге. Результат говорит, что изменилось в вагоне и почему.

Сохраняем тёмный характер и сиреневый акцент. Убираем дубли входа в модули, декоративную сцену из рабочего выбора, технические подписи и мотивационные числа из центра игрового экрана. Макет главной растёт по содержимому, а не обрезает кнопку фиксированной высотой.

## Границы

- Исходное приложение проверено в локальном браузере на отдельной БД в памяти. Все пять модулей пройдены по одной основной ветке; полный перебор графов не делался.
- Прототип использует только локальное состояние вкладки. Нет API v2, серверной паузы, защищённых наград, реальных рейтингов, полноценного движка или миграции. Он не импортирует frontend игры.
- Прототип демонстрирует ключевые маршруты и состояния, а не все возможные комбинации правил. Точные критерии и события реализуются и проверяются в будущем движке.
- Содержательные нормы классов обслуживания не выдумываются. Показан один синтетический вагон.
- Физический телефон, screen reader, тестирование с людьми, педагогическая валидность и production не проверены.

Frontend следует менять после согласования структуры и макетов. План обсуждения и задания для короткой пользовательской проверки — в [SCREENS](SCREENS.md).
